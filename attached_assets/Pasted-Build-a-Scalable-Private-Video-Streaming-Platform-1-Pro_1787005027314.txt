Build a Scalable Private Video Streaming Platform

1. Project Goal

Build a complete, production-ready web application for managing and streaming a private video library.

The platform should allow an administrator/owner to:

- Create and manage users.
- Create private groups.
- Assign users to groups.
- Upload videos.
- Import videos from supported external URLs where technically and legally permitted.
- Organize videos into folders/categories.
- Manually review every video before publishing.
- Approve, reject, archive, or delete videos.
- Stream approved videos to authorized users.
- Monitor storage usage and video statistics.
- Prepare the platform for future monetization and advertising.

The application must be designed for scalability.

The initial target is at least 100 GB of video storage, but DO NOT hard-code a 100 GB limit into the application. The storage architecture must allow the owner to expand beyond 100 GB later without rebuilding the application.

Do not store video binary files inside the relational database.

Use a proper object-storage/video-streaming architecture.

---

2. IMPORTANT CONTENT MODERATION REQUIREMENT

DO NOT automatically classify, reject, delete, hide, or block videos based on whether they appear to contain:

- Adult content
- Nudity
- Violence
- Offensive language
- Sensitive material
- Any other potentially inappropriate content

There must be NO automatic AI moderation decision that prevents publication.

Every uploaded/imported video must initially enter:

"PENDING_REVIEW"

The owner/admin manually reviews the video and decides what happens.

Available statuses:

- PENDING_REVIEW
- APPROVED
- REJECTED
- PRIVATE
- ARCHIVED
- PROCESSING
- FAILED

Only APPROVED videos should normally be visible to regular members.

The administrator must always be able to override the status manually.

---

3. USER ROLES

Implement role-based access control.

Roles:

OWNER

Full control over the entire platform.

Can:

- Manage administrators.
- Manage all users.
- Create/delete groups.
- Manage all videos.
- Review videos.
- Manage storage.
- Manage platform settings.
- View analytics.
- Manage future advertising settings.
- Change system configuration.

ADMIN

Can be granted configurable permissions by the Owner.

Examples:

- Manage users
- Manage groups
- Review videos
- Manage videos
- View analytics

Admins must NOT automatically receive Owner permissions.

GROUP_MANAGER

Can manage assigned groups and their content.

MEMBER

Can:

- Login.
- View groups they belong to.
- View approved videos available to them.
- Search videos.
- Watch videos.
- Resume watching.
- Add videos to favorites.

Members cannot:

- Upload videos unless explicitly granted permission.
- Approve videos.
- Manage users.
- See other private groups.
- Access administrative APIs.

- Logout.

5. DEVICE MANAGEMENT

Implement basic device/session management.

For every active session, store:

- User
- Device/session identifier
- Last activity
- Created date
- Approximate device/browser information

The user should be able to log out from all other sessions.

The Owner should be able to terminate suspicious sessions.

Prepare the system so a future plan can limit the number of active devices per account.

Each group can have:

- Name
- Description
- Cover image
- Status
- Created date
- Owner
- Members
- Categories
- Videos

Group visibility:

- PRIVATE

- SUSPENDED

User ↔ Groups

A user can belong to multiple groups.

A group can contain multiple users.

8. VIDEO UPLOAD

Implement video upload through the web application.

Requirements:

- Large file upload support.
- Upload progress.
- Cancel upload.
- Retry failed upload.
- Resume upload where supported.
- Validate file type.
- Validate file size.
- Generate thumbnail where possible.

Do not put large video files inside the database.

Use object storage/video streaming infrastructure.

The initial target storage capacity is 100 GB or more.

The architecture must allow storage expansion without changing application logic.

9. VIDEO IMPORT FROM URL

Create a feature:

"Import Video From URL"

The administrator can paste a video URL.

Example supported providers may include:

- YouTube
- X
- LinkedIn
- Facebook
- Instagram
- TikTok
- Direct video URLs
- Other technically supported providers

Do not promise universal compatibility.

The system must first detect the provider.

Architecture:

URL
→ Provider Detection
→ Supported?
→ Extract/Import
→ Download/Transfer where permitted
→ Process
→ Store
→ PENDING_REVIEW

If a provider is unsupported:

Return a clear error:

"This video source is currently unsupported."

If the URL requires authentication, DRM, or access that the system cannot legally/technically obtain, do not attempt to bypass it.

Never bypass:

- DRM
- Paywalls
- Authentication
- Access controls
- Copyright protection mechanisms

Only process content that the platform/user is authorized to import.

Use a modular provider architecture so new providers can be added later without rewriting the application.

16. STORAGE ARCHITECTURE

This is extremely important.

Do NOT make the database responsible for storing video files.

Create a storage abstraction layer.

Example:

"VideoStorageProvider"

Possible providers:

- Cloudflare Stream
- Cloudflare R2
- S3-compatible storage
- Other compatible object storage

The application should communicate with storage through a provider abstraction.

This means storage can be changed later without rewriting the entire application.

Initial target:

">= 100 GB"

Future target:

"100 GB → 500 GB → 1 TB+"

Do not hard-code a maximum storage limit.

Display storage usage in the Admin dashboard.

- An Owner can create users.
- An Owner can create Groups.
- Users can be assigned to Groups.
- A video can be uploaded.
- The video enters PENDING_REVIEW.
- Owner can manually review it.
- Owner can approve it.
- Approved video becomes available to authorized members.
- Unauthorized members cannot access it.
- Video can be streamed.
- Watch progress works.
- Search works.
- Favorites work.
- Storage usage is visible.
- The architecture supports at least 100 GB and can scale beyond that.
- No automatic content moderation blocks videos.
- External URL importing is modular and only works with supported/permitted sources.
- Critical security checks happen server-side.
- Errors are handled properly.
- The application works on mobile and desktop.

Start by analyzing this specification and proposing the exact architecture and technology stack before implementation.
